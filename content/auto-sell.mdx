# Auto-Sell

Premium-only feature. Automatically sells positions when take-profit or stop-loss triggers hit.

## Setup

User tells Claude: *"set auto-sell with 100% take profit and 50% stop loss"*

Claude calls `set_auto_sell(enabled=true, takeProfitPct=100, stopLossPct=50)`

Settings stored in `UserSettings`:

- `autoSellEnabled`: boolean
- `takeProfitPct`: percentage (min 25%) — global default
- `stopLossPct`: percentage (min 10%) — global default

Per-caller overrides can also be set on individual `AlphaGroup` entries. See [Alpha Callers](/alpha-callers).

### Minimums

- **Take Profit: 25% minimum** — lower values get triggered by normal volatility
- **Stop Loss: 10% minimum** — tighter stops get hit by slippage on illiquid tokens

## How It Works

Background job runs every 5 seconds (`src/services/auto-sell.js`):

```
1. Fetch all premium users with autoSellEnabled=true OR per-caller TP/SL set
2. For each user:
   a. Get all confirmed BUY trades (open positions)
   b. Batch-fetch AlphaGroup records for any alphaGroupId present on trades
   c. For each position:
      - Resolve effective TP/SL: callerOverride ?? globalSetting
      - Skip if neither is set for this holding
      - Use FIFO cost basis (proportional, not cumulative all-time spend)
      - Get current price (batched, 60s cache; pump.fun tokens priced sub-second over WSS)
      - Calculate unrealized P&L %
      - TP: if P&L >= effectiveTpPct → SELL (exact threshold)
      - SL: if P&L <= -(effectiveSlPct - slippageBuffer) → SELL (pre-trigger)
   d. Execute sell via orchestrator (uses on-chain balance for exact amount)
   e. Notify user in Telegram DM
```

## Per-Caller TP/SL Override

Each holding tracks the `alphaGroupId` of the caller whose call triggered the buy. At sell-check time, the job resolves:

```js
effectiveTpPct = alphaGroup?.takeProfitPct ?? settings.takeProfitPct
effectiveSlPct = alphaGroup?.stopLossPct   ?? settings.stopLossPct
```

This means:
- Positions from @degenwhale (TP 200%, SL 40%) fire at those thresholds
- Manually bought positions use global settings
- A user with no global TP/SL but per-caller overrides still gets auto-sell on those holdings

## Slippage-Aware Stop-Loss

The stop-loss triggers **before** the user's exact threshold so that after execution slippage + fees, the realised loss lands close to what the user set.

**Slippage buffer formula:**

```
slippageBufferPct = min((maxSlippageBps / 10000) * 100 * 0.2, 5)
```

It uses 20% of the user's max slippage setting as the estimated real slippage, capped at 5%.

| Max Slippage | Slippage Buffer | SL trigger (if user sets 50%) |
|---|---|---|
| 1500 bps (15%) | 3% | -47% |
| 2000 bps (20%) | 4% | -46% |
| 2500 bps (25%) | 5% (capped) | -45% |

**Why TP doesn't get a buffer:** take-profit fires at the exact threshold. Adding a buffer would mean never triggering on volatile memecoins — better to sell at target and receive slightly less after slippage than to overshoot and miss the exit entirely.

## Example

Settings: TP 100%, SL 50%, max slippage 1500 bps (15%) → SL buffer = 3%

- Bought 1000 DEGEN at $0.01 (cost: $10)
- Price hits $0.02 → P&L +100% → **TP triggered at 100%** → sells, actual realised may be 95-98% after slippage
- Price drops to $0.0053 → P&L -47% → **SL triggered at -47%** → after slippage, realised loss lands near -50%

## Dust + Grace Period Guards

- **Minimum position**: $0.50 — below this, gas cost exceeds the sell value
- **Grace period**: 5 minutes after a buy — prevents pump.fun buy-slippage (which can show -20% instantly) from firing a false stop-loss
- **Confirmed-empty cache**: tokens confirmed not held on-chain are skipped in the next cycles to avoid repeated Alchemy scans
- **Stablecoins excluded**: USDC/USDT on both chains never trigger TP/SL
- **Dust epsilon**: positions below `0.000001` held are filtered (floating-point residue after selling)

## Rug Exit (Emergency Sell)

Beyond take-profit and stop-loss, the agent runs an **always-on rug detector** that
closes a position the moment its price collapses — protecting against rugs and LP
pulls that stop-loss can't catch.

**How it differs from stop-loss:** it's velocity-based, not threshold-based. Stop-loss
says *"sell at -25% from my cost."* The rug detector says *"the price just fell off a
cliff from where it was minutes ago"* — regardless of your cost or your SL setting.

**Signal:** a drop of **≥ 50%** from the token's rolling peak within a **180-second**
window (`src/services/rug-detector.js`). On trip, the agent sells 100% immediately and
sends a single **🚨 Rug Exit** notification (same execution path as stop-loss).

**What it catches that stop-loss can't:**

- **Rugs during the grace period** — stop-loss is intentionally off for the first 5
  minutes after a buy (to ignore entry slippage); the rug detector still fires.
- **Collapses when SL is loose or off** — a sudden crash exits even with no stop-loss set.
- **The event, not a fixed loss number** — it reacts to the *speed* of the fall.

No setup required — it's core agent behaviour, on for everyone using auto-sell. The
sensitivity is a conservative default tuned to a real collapse (not a normal wick); it
can be tuned via `RUG_DROP_PCT` / `RUG_WINDOW_SECS` if ever needed.

## Real-Time Pricing (WSS)

For pump.fun bonding-curve tokens — the freshest, most volatile memecoins where fast
exits actually win money — Pantr subscribes to the bonding-curve account directly over
an RPC WebSocket (`src/services/price-stream-manager.js`) and recomputes price the
instant on-chain reserves change. This is the **same reserve decode** that
`pumpswap-direct` uses to execute real swaps, so it's already trusted.

- **Sub-second, no REST rate limits** for held pump tokens — feeds both the price cache
  the auto-sell loop reads and the rug detector's velocity window in real time.
- **Graceful fallback:** any RPC/subscribe failure falls back to the REST price path —
  the stream can only make pricing fresher, never break it.
- **Scope:** pump.fun bonding curves on Solana. Graduated/AMM tokens and EVM/TON use the
  REST price path. Subscriptions match exactly the Solana tokens currently held.

## Actual P&L Reporting

The trigger fires on an estimated P&L (current price × held tokens vs cost basis). After the sell confirms, the actual realised P&L is recalculated using FIFO cost basis from the confirmed sell trade's `amountOutUsd`, so the user's Telegram notification shows the **real** P&L — not the trigger-time estimate.

## Activity Gate

The auto-sell job respects the activity gate — if no users are active, it skips DB queries to let Neon sleep.
