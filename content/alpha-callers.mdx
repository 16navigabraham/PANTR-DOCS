# Alpha Callers

Alpha callers are Telegram users whose contract address (CA) posts trigger automatic buys for subscribers. Pantr reads their messages through the subscriber's own Telegram account via MTProto — no bot needs to be added to any group.

## How It Works

1. **Connect account** — user runs `/trackalpha`, enters their phone number and OTP
2. **Add callers** — tell Claude which caller to watch in which group
3. **Pantr listens** — a persistent MTProto connection reads messages from those groups through the user's own account
4. **Auto-buy fires** — when a tracked caller posts a CA, Pantr executes a buy and DMs the user

Pantr reads through the user's own account rather than needing elevated group permissions.

## Why MTProto, Not Bot-in-Group

| Approach | Problem |
|----------|---------|
| Add bot to group | Most alpha group admins block bots |
| Bot polls | No push — latency, rate limits |
| MTProto (user session) | Push-based TCP — instant delivery, no admin permissions needed |

Telegram pushes new messages to the connected client in real time. There is no polling.

## Supported Group Types

| Type | Supported | Notes |
|------|-----------|-------|
| Public supergroup | ✅ | Identify by `@handle` |
| Private supergroup | ✅ | Identify by `t.me/+inviteHash` |
| Broadcast channel | ✅ | Raw `UpdateNewChannelMessage` handler — `NewMessage` event misses these |
| Legacy group | ✅ | Rare; works the same way |

```

      → "Code sent — add a letter before the digits, e.g. x12345"

      → _saveSession() saves StringSession to DB

User: "watch @degenwhale in @solanagems"
Claude: → manage_alpha_callers(action='add', callerUsername='degenwhale', groupUsername='@solanagems')
```

## Message Detection Flow

Pantr uses two complementary event handlers. `NewMessage` covers supergroups and legacy groups; `Raw` catches broadcast channels which `NewMessage` silently drops.

```
Message posted in tracked group/channel
        |
        ├── Supergroup / legacy group
        |         NewMessage event fires
        |         → getSender() → match callerUsername or senderId
        |         → entityIdToGroupKey lookup
        |         → handleMtprotoMessage()
        |
        └── Broadcast channel
                  Raw(UpdateNewChannelMessage) fires
                  → peerId.channelId extracted
                  → reverse-iterate callerEntityMap to find owner
                  → handleMtprotoMessage()

handleMtprotoMessage():
    1. MD5 dedup check (per userId:callerUsername:hash) — skips re-processing same message text
    2. Check user.isPaused AND settings.alphaPaused
    3. Sniper window check
    4. Parse CA from message text
    5. Per-user+caller+CA dedup — skips re-buying same token if caller posts updates
    6. Safety check on token
    7. Execute buy via orchestrator (or simulateSell in demo mode)
    8. DM user with rich card (symbol, MC, liq, price, tx hash, explorer links)
```

**Key internal details:**
- `callerEntityMap` is keyed by caller username (not entity ID). The Raw handler reverse-iterates the map to find which caller owns the incoming channel ID — direct key lookup by ID would always miss.
- Both `NewMessage` and `Raw` handlers share an in-memory `_handledMsgIds` Set keyed by `chatEntityId:msgId` with a 5s TTL. This prevents the same message from being processed twice when both handlers fire for a broadcast channel post.

## Managing Callers

Via the `manage_alpha_callers` tool (Claude handles this conversationally):

| Action | Description |
|--------|-------------|
| `add` | Subscribe to a caller in a specific group |
| `update` | Change strategy for an existing caller |
| `remove` | Unsubscribe from a caller |
| `list` | Show all tracked callers with their strategy |
| `pause` | Temporarily stop a caller's auto-buys |
| `resume` | Re-enable a paused caller |
| `pause_all` | Pause every active caller at once |
| `resume_all` | Resume every paused caller at once |

**`add` requires both `callerUsername` and `groupUsername`.** The user must have connected their TG account first via `/trackalpha` — if no session exists, Claude tells them to run it.

## Per-Caller Strategy

Each `AlphaGroup` entry can have its own trading strategy independent of global settings:

| Field | Description |
|-------|-------------|
| `buyAmountUsd` | Override buy amount for this caller. Falls back to global setting |
| `takeProfitPct` | Override take-profit for positions from this caller's calls |
| `stopLossPct` | Override stop-loss for positions from this caller's calls |

Natural language configures everything in one message:
> *"watch @degenwhale in @solanagems, buy $25, take profit at 200%, stop loss at 40%"*

Claude chains `manage_alpha_callers` with all fields in one call. The `alphaGroupId` is stored on each `Trade` record so auto-sell knows which caller's TP/SL to apply.

## Session Management

- One `TelegramClient` (gramjs) per user, held in memory
- `StringSession` persisted in `user_telegram_sessions` table
- On server restart, `startAll()` reconnects all users in batches of 5
- `refreshSubscriptions()` rebinds event handlers after caller add/remove
- 2FA accounts: fully supported — Telegram's native confirmation dialog handles 2FA on the user's device, Pantr never sees the password

## Database Models

```prisma
model AlphaGroup {
  id             String   @id @default(uuid())
  userId         String
  groupUsername  String?  // @handle or t.me/+hash
  groupTitle     String?
  callerUsername String   // without @
  isActive       Boolean  @default(true)
  tradesExecuted Int      @default(0)
  buyAmountUsd   Decimal? @db.Decimal(18, 6)
  takeProfitPct  Decimal? @db.Decimal(5, 2)
  stopLossPct    Decimal? @db.Decimal(5, 2)
  @@unique([userId, callerUsername, groupUsername])
}

model UserTelegramSession {
  id            String   @id @default(uuid())
  userId        String   @unique
  sessionString String
  phone         String?
  connectedAt   DateTime @default(now())
}
```

## Log Messages

| Message | Meaning |
|---------|---------|
| `MTProto: alpha message detected` | Supergroup/legacy group message from tracked caller; CA extraction starting |
| `MTProto: alpha channel message detected (raw)` | Broadcast channel message from tracked caller via Raw handler; CA extraction starting |
| `[ALPHA:MTPROTO] no CA in message` | Caller posted but no contract address found (image, text, meme) — expected noise, not an error |
| `MTProto: tracking callers` | Informational — lists callers being watched for a user at listener boot |
| `MTProto: entity ID mismatch for tracked caller` | A tracked caller posted in a group they're not registered for — blocked correctly |

The `no CA in message` log fires often for active callers who post non-trade content. It is not actionable.

## Privacy

When a user mentions the bot in a group asking about balance, portfolio, or trading:

- Bot detects privacy-sensitive request
- Responds in group: "Check your DMs!"
- Processes the request in the user's DM

Public queries (token price, safety, trending) are answered directly in the group.
