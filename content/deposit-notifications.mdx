# Deposit Notifications

Real-time alerts when a user receives SOL, ETH, or USDC into their Pantr wallet. Powered by websocket subscriptions with **server-side filtering** so cost scales with `O(users)` delivery, not with chain activity.

Service: `src/services/deposit-monitor.js`

## Why Server-Side Filtering Matters

A naive "subscribe to all USDC Transfer events and filter client-side" implementation looks clean but is catastrophic on a paid RPC:

- USDC on Base processes **hundreds of `Transfer` events per minute**
- Alchemy bills WebSocket subscriptions at `0.04 CU per byte delivered` (~40 CU per event)
- Even with zero deposits, you burn ~10M+ compute units per day just receiving events you throw away

The fix is to push filtering to the RPC provider. Alchemy delivers only events that match — for a handful of users with no active deposits, that's ~zero events per day.

## Coverage

| Chain | Token | Mechanism |
|-------|-------|-----------|
| Solana | SOL (native) | `onAccountChange` per wallet → lamport balance delta |
| Base | USDC | `eth_subscribe('logs', …)` with recipient (`topics[2]`) filtered to tracked wallets |
| Base | ETH (native) | `eth_subscribe('alchemy_minedTransactions', …)` with `to` address filter |
| BSC | USDC | `eth_subscribe('logs', …)` with recipient filter (Alchemy websocket) |
| BSC | BNB (native) | `eth_subscribe('alchemy_minedTransactions', …)` with `to` address filter |
| Mantle | MNT (native) | Polling every 30s via JSON-RPC `getBalance()` |
| TON | TON (native) | Polling every 45s via TonWeb client |

### Minimum thresholds

Tiny dust transfers are ignored to avoid notification spam:

- SOL: `0.0001`
- ETH: `0.00001`
- BNB: `0.001`
- MNT: `0.01`
- TON: `0.1`
- USDC: `0.01`

## Architecture

```
┌───────────────────────┐    ┌────────────────────────────────┐
│  Solana RPC (WSS)     │    │  Base WSS (Alchemy)            │
│  onAccountChange      │    │  logs[USDC, topics[2]=users]   │
│  per wallet           │    │  alchemy_minedTransactions     │
│                       │    │    {addresses: [{to: user}]}   │
└──────────┬────────────┘    └──────────┬─────────────────────┘
           │                            │
           └─────────────┬──────────────┘
                         ▼
            ┌────────────────────────┐
            │    DepositMonitor      │
            │  solWallets: Map       │  (base58, case-preserved)
            │  evmWallets: Map       │  (lowercased 0x)
            │  baseSubs: Map         │  (sub id → 'usdc' | 'eth')
            └────────────┬───────────┘
                         ▼

            │ .sendDepositReceived() │
            └────────────┬───────────┘

              TG DM + WS emit
```

## Flow

1. **On startup** — `DepositMonitor.start()` loads every active wallet from the DB into two in-memory maps (split by chain because Solana base58 is case-sensitive, EVM is not).
2. **Solana** — calls `onAccountChange(pubkey)` for each SOL wallet. The handler tracks the previous lamport balance and fires `handleDeposit` on any positive delta ≥ threshold.
3. **Base USDC** — single `eth_subscribe('logs', {...})` with `address: USDC_CONTRACT` and `topics: [Transfer, null, [paddedUser1, paddedUser2, ...]]`. Alchemy only delivers events where `topics[2]` (the indexed recipient) matches a tracked wallet. Client-side is just `handleBaseUsdcLog` decoding the amount and firing.
4. **Base ETH** — single `eth_subscribe('alchemy_minedTransactions', {addresses: [{to: wallet}, ...]})`. Alchemy delivers only txs with a matching `to` address. Handler reads `tx.value` and fires.
5. **On new wallet** — `wallet-service.createWallet()` calls `depositMonitor.addWallet(address, userId, chain)`. For Base, this triggers `resubscribeBase()` which unsubscribes the old filters and recreates them with the updated wallet set (ensures the new user is covered without a restart).

## Raw WebSocket, Not ethers.WebSocketProvider

Base monitoring uses a raw `ws` WebSocket directly rather than `ethers.WebSocketProvider`. Two reasons:

1. **Custom subscription types** — `alchemy_minedTransactions` is an Alchemy-specific method. Ethers provider abstracts subscriptions and doesn't cleanly expose arbitrary ones.
2. **Message routing** — with custom subs, we need to read raw JSON-RPC responses to map subscription IDs back to subscription types (`'usdc'` vs `'eth'`).

`handleBaseWsMessage()` parses each incoming frame and routes it:

- `{ id, result: "0x<subId>" }` → store `subId → type` mapping
- `{ method: "eth_subscription", params: { subscription, result } }` → look up type and dispatch to `handleBaseUsdcLog` or `handleBaseMinedTx`

## WS Crash Protection

Base WebSocket connection uses a two-step handshake to prevent server crashes:

1. Create a raw `WebSocket` with an error handler attached
2. If handshake fails (e.g. 429 rate limit), resolve `null` instead of throwing
3. Only proceed with subscriptions after successful handshake

Without this, a rejected handshake throws an uncaught async error that crashes the Node process. On Render, this previously triggered an immediate restart → another 429 → crash loop.

## Notification

`notifications.sendDepositReceived(userId, { chain, token, amount, amountUsd, txHash })` formats a Telegram DM:

```
💰 Deposit Received!

🟣 0.25 SOL (~$21.06)
Chain: SOLANA

[View Transaction]
```

It also emits a `deposit:received` WebSocket event for the dashboard.

## Reconnect

Base WS reconnects with exponential backoff (1s → 30s max, capped at 10 attempts) on `close` or handshake failure. After 10 failed attempts, Base monitoring is disabled until the next server restart. Subscription state is cleared and rebuilt from the in-memory wallet map, which is the source of truth.

Solana reconnects are handled by `@solana/web3.js` Connection internally.

## Trade Suppression

When a user executes a trade, the resulting balance change should not trigger a deposit notification. Two mechanisms handle this:

### EVM (Base) — TX Hash Filtering

`registerTradeTx(txHash)` adds the trade's transaction hash to a `recentTradeTxHashes` Set with a 60-second TTL. When `handleDeposit` fires, it checks if the txHash matches a recent trade and skips the notification.

### Solana — User-Level Suppression

Solana's `onAccountChange` doesn't provide a transaction hash, so txHash filtering can't work. Instead, `suppressUser(userId)` adds the user to a `suppressedUsers` Set with a 60-second TTL. Any deposit detected for that user during the window is silently ignored.

Both mechanisms are triggered from the trade orchestrator's `onTxSent` hook, which passes `{ txHash, userId }`.

## Config

```env
# Required for Base monitoring (native ETH + USDC)
BASE_WS_URL=wss://base-mainnet.g.alchemy.com/v2/<key>

# Solana uses the existing RPC URL (must be WS-capable)
SOLANA_RPC_URL=https://mainnet.helius-rpc.com/?api-key=<key>
```

Without `BASE_WS_URL`, Base monitoring is skipped with a warning — Solana still works.

## Previous Broken Implementation (For Reference)

Before 2026-04-14, the Base monitor used two mechanisms that burned ~300M Alchemy compute units in days:

1. **Full block scans every 2s** — `on('block', ...)` + `getBlock(n, true)` pulled full tx lists for every mined block regardless of tracked wallets.
2. **Unfiltered USDC log subscription** — subscribed to every `Transfer` event on the USDC contract with client-side filtering. USDC delivers hundreds of events per minute on Base; every one was billed before being thrown away.

Both were replaced with the server-side filtered subscriptions documented above. Do not revert.

## Not Covered (Yet)

- **Solana USDC** — arrives at the wallet's Associated Token Account (ATA), a derived address. Needs a separate `onAccountChange` subscription on each user's USDC ATA. Planned as a follow-up.
